# Decisiones de diseño

Registro corto de decisiones (formato ADR simplificado). Sirve para explicar el proyecto en una entrevista sin improvisar.

## ADR-001 · El grafo se construye en memoria

**Contexto:** la malla vive en PostgreSQL; las consultas de prerrequisitos son recursivas.

**Decision:** cargar la carrera completa y construir el `CurriculumGraph` en memoria en cada request.

**Por qué:** una malla tiene decenas de materias, no millones. Cargar 46 filas es mas barato que una CTE recursiva, y permite que el motor sea Java puro, testeable sin Spring ni base de datos.

**Consecuencia:** si el catalogo crece a miles de carreras, habra que cachear por `careerCode` (Caffeine) o materializar el grafo.

## ADR-002 · H2 en desarrollo, PostgreSQL en produccion

**Contexto:** la app tiene que arrancar con un solo comando para cualquiera que clone el repo.

**Decision:** H2 en modo PostgreSQL para el perfil por defecto; PostgreSQL real en `application-postgres.yml` y en Docker Compose. Flyway aplica el mismo SQL portable en ambos.

**Por qué:** cero friccion para el reclutador que quiere probar el proyecto. El SQL usa `GENERATED BY DEFAULT AS IDENTITY`, `VARCHAR`, `TIMESTAMP`, todo soportado por ambos motores.

**Consecuencia:** no se pueden usar tipos exclusivos de PostgreSQL (`jsonb`, `array`, `tsvector`) sin una migracion especifica.

## ADR-003 · Planificador voraz y determinista

**Contexto:** el problema general de scheduling academico es NP-hard.

**Decision:** heuristica voraz por semestre, ordenada por profundidad critica, impacto y semestre sugerido.

**Por qué:** planes explicables, reproducibles y testeables. Un plan "optimo" que el estudiante no entiende no sirve.

**Consecuencia:** el plan puede no ser el minimo absoluto cuando el tope de creditos es muy ajustado. Se mitiga mostrando el minimo teorico al lado.

## ADR-004 · React Flow en vez de D3

**Contexto:** habia que dibujar un DAG interactivo con zoom, paneo y nodos personalizados.

**Decision:** `@xyflow/react` con posiciones calculadas por semestre.

**Por qué:** D3 da control total pero exige implementar zoom, arrastre, handles y minimapa. React Flow ya lo resuelve y deja el esfuerzo en el diseño de los nodos y en la logica.

**Consecuencia:** se depende de una libreria de UI; el layout es propio (columnas por semestre), no automatico.

## ADR-005 · API sin estado con persistencia opcional

**Contexto:** la UI simula en vivo mientras el usuario hace clic.

**Decision:** `POST /api/planner/simulate` no escribe en la base salvo que el cliente mande `"save": true`.

**Por qué:** evita llenar la tabla de simulaciones con cada clic, y mantiene el endpoint puro (misma entrada, misma salida), lo que simplifica cache y tests.

**Consecuencia:** el historial solo contiene escenarios que el usuario decidio guardar.

## ADR-006 · CSS propio en vez de Tailwind

**Contexto:** el frontend necesitaba un look distintivo y pocas pantallas.

**Decision:** un unico `styles.css` con variables CSS y componentes nombrados.

**Por qué:** menos dependencias, control total del detalle visual (glows, gradientes del grafo) y cero configuracion extra para quien clona el repo.

**Consecuencia:** si el proyecto crece a muchas pantallas, conviene migrar a Tailwind o CSS Modules para evitar colisiones de nombres.
